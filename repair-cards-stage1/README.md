# Карточки ремонта — этап 1

Это первый рабочий этап: база SQLite и локальный сервер на C++.
Оконные приложения «Ридер» и «Креатор», свободный редактор таблиц, генерация QR и печать Zebra идут следующими этапами.

## Что можно проверить сейчас

1. Добавить тип платформы.
2. Ввести начальный ID продукции и количество карточек.
3. Проверить диапазон до регистрации.
4. Создать партию. SQLite назначает каждой записи собственный внутренний номер.
5. Открыть список в браузере и отфильтровать его по типу платформы.
6. Открыть предварительный просмотр карточки.
7. Перезапустить сервер и убедиться, что записи сохранились.

У каждой карточки сохраняется отдельная бинарная копия вашего `blank.xlsx` внутри SQLite.
На этом этапе XLSX еще не заполняется: ID хранится в учетных полях базы и отображается в предварительном просмотре.
Предварительный просмотр воспроизводит структуру образца, но пока не является редактором Excel.

## Шаг 1. Открыть в CLion

Используем **CLion и MinGW64**, уже установленные у пользователя. Visual Studio не требуется.
Полная инструкция: `docs/CLION.md`.

1. Распакуйте проект, например в `C:\RepairCards\stage1`.
2. В CLion выберите **File → Open** и папку с `CMakeLists.txt`.
3. В **Settings → Build, Execution, Deployment → Toolchains** выберите MinGW и проверьте определение `gcc.exe` и `g++.exe`.
4. В настройках **CMake** выберите этот Toolchain, **Debug**, каталог сборки `build/mingw-debug`. Генератор можно оставить по умолчанию (Ninja).

Все библиотеки проекта уже включены. Qt, отдельный SQLite, Python и Node.js для запуска не требуются.
Существующие базы не ищем и не подключаем автоматически: создается новая база проекта.

## Шаг 2. Настроить запуск

В **Run → Edit Configurations** для цели **repair_server**:

- **Program arguments:** `--config config.example.json`
- **Working directory:** корень проекта, где находятся `CMakeLists.txt` и `config.example.json`.

## Шаг 3. Собрать

Выберите цель **repair_server** и нажмите Build.
Для проверки ядра можно отдельно запустить цель **core_tests**: результат `Core tests passed`.
При ошибке сохраните первую ошибку компилятора и версию выбранного GCC.

## Шаг 4. Запустить сервер

Нажмите Run для **repair_server**. Окно консоли оставьте открытым.

Ожидаемый вывод:

```text
Repair Cards 0.1.0
Database: .../data/repair.sqlite3
Listen: http://127.0.0.1:8080
Stop: Ctrl+C
```

Откройте http://127.0.0.1:8080. Пока список будет пустым.
На первом этапе проверяем на вашем ПК. Конфигурация пока слушает только этот компьютер.
Если порт 8080 занят, для его смены нужно изменить `port` в конфигурации и `$base` в `scripts/demo.ps1`.

Скрипты `01_build.cmd` и `02_start_server.cmd` — необязательная альтернатива запуску из IDE.
Для `01_build.cmd` CMake и MinGW должны находиться в PATH; при работе в CLion это не требуется.

## Шаг 5. Создать первую партию

Оставив сервер работающим в CLion, запустите `03_demo.cmd`. Это временный помощник для проверки сервера, а не окончательный Креатор.

Введите по очереди:

```text
Platform name: Ноутбук 16.5
First product ID: V00001
Number of cards: 5
```

Помощник покажет будущий диапазон. Введите `YES`, чтобы создать именно эту партию.
После создания откроется список в браузере. Будут видны внутренние номера и введенные ID продукции.
Кнопка «Открыть» ведет в предварительный просмотр бланка.

Повторный запуск помощника снова создает записи после подтверждения: одинаковые ID продукции разрешены, это не операция обновления.
Следующий ID хранится отдельно у каждого типа платформы и предлагается API будущему Креатору.
Временный помощник пока просит вводить начальный ID вручную.

## Шаг 6. Проверить сохранение

1. Остановите сервер кнопкой Stop в CLion.
2. Снова запустите цель `repair_server`.
3. Обновите страницу. Карточки должны остаться.

Главный файл данных: `data/repair.sqlite3`. Если сервер запущен, рядом могут находиться файлы `-wal` и `-shm`; это нормальная работа SQLite.
Для простой резервной копии остановите сервер и скопируйте всю папку `data`.
Не удаляйте рабочую базу ради сброса нумерации: внутренние номера определяют ссылки на карточки.

## Следующие этапы

1. **Этот этап:** регистрация, SQLite, API, проверка сохранения и фильтрации.
2. **Креатор и редактор:** отдельное приложение, выбор типов через список и «+», предпросмотр партии, редактирование бланка с добавлением строк и столбцов, сохранение документа. При одновременных правках — проверка версии документа, чтобы не затирать изменения.
3. **Ридер и QR:** отдельное приложение только для просмотра; QR ведет на конкретную карточку по внутреннему ID. Подключение компьютеров и телефонов в вашей сети.
4. **Zebra:** выбор установленного Windows-принтера, размер этикетки, ориентация, качество и печать партии. Для этого потребуются модель Zebra и размеры этикеток.

Учетных записей, паролей и печати бланков в требованиях нет.
Первый сервер также не содержит авторизации: это база для двух клиентов, а не система разграничения доступа по пользователям.

## Для разработчика

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
python tests/api_test.py build/repair_server
```

На Windows вне CLion, если инструменты доступны в PATH:

```powershell
cmake -S . -B build/mingw64 -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++
cmake --build build/mingw64 --parallel 2
ctest --test-dir build/mingw64 --output-on-failure
```

Конфигурация читается через `repair_server --config config.example.json`.
Пути базы и шаблона считаются относительно файла конфигурации.
Название базы задается в JSON: проект не ищет и не подключает существующие базы автоматически.

Подробности API и правил: `docs/API.md` и `docs/REQUIREMENTS.md`.
