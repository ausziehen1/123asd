# Repair Cards 0.6.0 — установка, совместная работа и обновление

## 1. Что находится в комплекте

На одном постоянно включенном Windows-ПК работают `repair_server.exe` и SQLite. База лежит на его **локальном диске**. Все пользователи обращаются к серверу по HTTP; копировать базу на пользовательские ПК или открывать ее через сетевую папку не требуется.

Пользователям передается **один файл** нужного приложения из папки `clients` полного архива:

| Файл | Назначение |
|---|---|
| `Creator.exe` | Типы продукции, регистрация диапазонов, редактирование бланков, коды 1С, QR и BarTender |
| `Reader.exe` | Ввод/сканирование и просмотр существующего бланка |
| `Repair.exe` | Ввод/сканирование, редактирование и сохранение существующего бланка |

Эти EXE самодостаточны для распространения: нужные DLL, обновляющий модуль и справка встроены в файл. При первом запуске EXE распаковывает их в `%LOCALAPPDATA%\RepairCards\clients\НазваниеПриложения\идентификатор-комплекта`. Права администратора для распаковки не нужны. Рабочие бланки остаются на сервере. Установка приложения в Program Files не требуется.

**Системный компонент:** для встроенного окна бланка нужен Microsoft Edge WebView2 Runtime Evergreen x64. На многих ПК он уже установлен. Если приложение сообщает об отсутствии Runtime, установите его один раз с [официальной страницы Microsoft](https://developer.microsoft.com/microsoft-edge/webview2/#download-section). В корпоративной сети ИТ-отдел может установить Evergreen Standalone Installer x64 без доступа клиентского ПК к Интернету. WebView2Loader.dll уже встроен в наш EXE; он не заменяет Runtime.

Creator для макета/печати использует установленный **BarTender 10.1 SR3** и драйвер Zebra S4M ZPL. Reader и Repair не требуют BarTender или Excel. Excel не требуется и для обычного редактирования бланка в Creator.

В `ready-windows` также лежит обычный комплект EXE + DLL для администратора и разработки. Его EXE нужно хранить с соседними DLL. **Для раздачи одного файла берите EXE из `clients`, а не маленькие EXE из `ready-windows`.**

## 2. Первый запуск нового сервера

Если у вас уже есть записи, переходите к разделу 3 — обновление существующего проекта.

1. Распакуйте полный архив целиком, например в `C:\RepairCards`. Внутри найдите папку проекта с `ready-windows`, `templates`, `web`, `clients`.
2. В `ready-windows` скопируйте `config.example.json` в **`config.local.json`**.
3. Откройте `config.local.json` Блокнотом. Типовой конфиг:

```json
{
  "host": "0.0.0.0",
  "port": 8080,
  "database": "../data/repair.sqlite3",
  "template": "../templates/blank.xlsx",
  "web": "../web",
  "public_url": ""
}
```

Пути отсчитываются от папки конфига. `../data/repair.sqlite3` означает `data` в корне проекта, уровнем выше `ready-windows`. SQLite и таблицы создаются автоматически. Отдельно создавать таблицы вручную не нужно. `host: 0.0.0.0` разрешает подключения по сети, но не является адресом для ввода у пользователя.

4. Запустите **`ready-windows/START-SERVER.cmd`**. Он использует `config.local.json`, если этот файл есть; иначе — пример конфига. В консоли должны появиться `Repair Cards 0.6.0`, путь вашей базы и порт. Оставьте консоль открытой.
5. На серверном ПК проверьте `http://127.0.0.1:8080/api/health` в браузере: ожидаются `status: ok`, `version: 0.6.0`, `schema: 5`.
6. Узнайте сетевой IPv4 адрес сервера командой `ipconfig`, например `192.168.10.20`. На другом ПК откройте `http://192.168.10.20:8080/api/health`. Если ответа нет, проверьте маршрут/корпоративный межсетевой экран и входящий TCP-порт 8080 на сервере. Настройку корпоративных правил выполняет ваш ИТ-отдел.
7. Закрепите IP сервера в DHCP или согласуйте постоянное DNS-имя. В QR сохраняется этот адрес. `127.0.0.1` на чужом ПК означает чужой ПК и для сетевых QR не подходит.
8. Запустите `clients/Creator.exe`, введите сетевой адрес, нажмите «Подключить» и добавьте тип платформы кнопкой «+».

Для запуска после входа в Windows можно создать ярлык на `START-SERVER.cmd` в папке `Win+R → shell:startup`. В этом варианте сервер запускается **после входа пользователя**. Если работа нужна до входа, настройте через ИТ-отдел задачу Планировщика при запуске системы: программа `repair_server.exe`, аргументы `--config "полный путь к config.local.json"`. Не настраивайте одновременно несколько способов запуска. Для одной базы должен работать один сервер.

## 3. Обновление с 0.5.0 и более ранних версий

Этот переход включает изменение сервера и схемы базы. Клиентского DLL-патча для него недостаточно.

1. Попросите пользователей сохранить бланки и закрыть старые приложения. Остановите старый сервер.
2. Сделайте резервную копию **всей прежней папки `data`** и своего конфига. Дополнительно сохраните `%LOCALAPPDATA%\RepairCards` на ПК, где есть рабочий макет BarTender. При остановленном сервере папку `data` можно копировать Проводником.
3. Распакуйте новую версию **в отдельную папку**. Старую папку пока оставьте резервной. Не запускайте в ней прежний сервер.
4. Скопируйте прежнюю папку `data` в корень нового проекта. Если база находилась в другом месте или называлась иначе, перенесите ее папку после остановки сервера и укажите фактический путь. Не создавайте новую пустую базу вместо прежней.
5. В новой `ready-windows` создайте `config.local.json` из примера. Укажите путь перенесенной базы, прежний порт, `../templates/blank.xlsx` и `../web`. Свою измененную Excel-болванку перенесите в `templates`. Важно сохранить прежние сетевой адрес и порт: тогда уже напечатанные QR продолжат открывать те же Unique ID.
6. Запустите новый `START-SERVER.cmd`. В консоли проверьте **версию и путь базы**. Схема обновится до **5** автоматически; карточки, внешние номера, бланки, настройки публичного QR-адреса и идентификатор сервера сохраняются.
7. Запустите новый `clients/Creator.exe` и проверьте прежние записи, пару бланков и один старый QR.
8. Раздайте пользователям новые однофайловые Reader/Repair/Creator. Старые версии не используют новую очередь и живое обновление, поэтому для заявленного режима совместной работы обновить нужно **все клиенты**.

Не запускайте старый сервер с уже обновленной базой. Для возврата к старой версии остановите новый сервер и восстановите **копию базы до миграции** вместе со старой программой.

Рабочий `%LOCALAPPDATA%\RepairCards\labels\RepairCards.btw` остается на месте. Если ранее уже связали QRUrl и OneCCode, повторно настраивать их не нужно.

## 4. Как работают несколько пользователей

Можно одновременно запускать несколько экземпляров одного EXE: два Creator, несколько Reader и Repair, на одном ПК или на разных. Каждый экземпляр имеет собственное состояние открытого бланка и отдельный профиль WebView2. Первая одновременная распаковка одного EXE защищена межпроцессной блокировкой.

Все операции с SQLite проходят через серверную **FIFO-очередь**. SQLite работает в WAL-режиме с транзакциями и `synchronous=FULL`. Регистрация диапазона, назначение кодов, сохранение бланка и запись истории выполняются целиком; частичного сохранения половины диапазона нет. Второй экземпляр нового сервера не сможет открыть ту же базу даже на другом порту.

Правила новых Creator/Repair:

- Два человека изменили **разные ячейки** одного бланка: сохраняются оба изменения. При сравнении используется версия, с которой каждый начал редактирование; весь устаревший бланк поверх нового не записывается.
- Два человека изменили **одну ячейку**: побеждает изменение, обработанное очередью последним. Окна разрешения конфликтов не появляются. Порядок определяется приемом операции серверной очередью, а не часами пользовательских ПК.
- Меняется структура листа: число строк/столбцов, объединения, состав или порядок листов. Для пересекающихся структурных изменений более поздняя операция заменяет затронутый лист целиком; изменение состава листов заменяет книгу. Программа не угадывает координаты перемещенных ячеек. Предыдущие варианты доступны через «История».
- Коды 1С тоже назначаются по очереди. Если затем меняется эта же ячейка в Repair, применяется соответствующее более позднее изменение.
- Повторная передача **того же** запроса сохранения или регистрации с тем же служебным номером не создает повторную операцию. Если человек заново сознательно формирует диапазон, это новая регистрация.
- Unique ID всегда уникален и создается базой. Table ID берется из введенного начального номера и не сдвигается автоматически из-за действий другого Creator. По прежним правилам внешние Table ID могут повторяться, в том числе при отдельной регистрации: отличать карточки нужно по Unique ID и типу платформы.

Бланки автоматически проверяют обновления примерно **раз в секунду**, списки Creator — **раз в три секунды**. При завершенном вводе изменения появляются без ручной кнопки обновления. Содержимое ячейки, в которой сейчас печатают, не прерывается: обновление применяется после завершения ввода. Несохраненные местные правки сохраняются в окне. Если приложение было свернуто/вкладка неактивна, проверка выполняется при возвращении к нему.

При обрыве сети показана последняя загруженная версия и сообщение об отсутствии связи. Правки остаются в окне; после восстановления связи обновления возобновляются. Для сохранения нужен сервер. Это сетевой клиент, а не автономная офлайн-копия базы. Перед закрытием несохраненный вариант можно скачать кнопкой **«Скачать мои правки (XLSX)»**.

«Актуальная информация» означает последние **сохраненные** изменения. Текст, который человек еще не сохранил, другим пользователям не показывается. Бланки больших размеров, загрузка сервера и задержка сети могут увеличить время обновления.

## 5. Диапазоны, коды 1С и печать

### Сформировать диапазон

1. В Creator подключитесь к серверу.
2. Выберите тип платформы из списка; если его нет, добавьте «+».
3. Введите **начальный Table ID** и количество, например `V00001` и `10`.
4. «Просмотр» показывает диапазон без регистрации. «Сформировать диапазон» после подтверждения регистрирует карточки.
5. Для каждого типа следующий номер предлагается отдельно. Данные предложения обновляются при работе других Creator, но введенный вручную номер сохраняется.
6. Выберите строки списка с Ctrl/Shift либо нажмите «QR последней партии».

### Распределить коды 1С

В «QR / BarTender» показано «Количество номеров». Слева задайте группы:

| Количество | Код 1С |
|---:|---|
| 2 | 123 |
| 7 | 1234 |
| 1 | 12345 |

Плюс справа у **последней строки** добавляет группу. Минус у предыдущих удаляет группу. Для общего кода достаточно `10 / один код`. Для пустого кода оставьте второе поле пустым. Код — текст; ведущие нули сохраняются.

Сумма количеств должна равняться количеству выбранных карточек. Справа показано точное назначение **Unique ID / Table ID / 1C Code** в порядке списка. Проверьте его перед «Сформировать QR».

Код сохраняется в SQLite (`cards.one_c_code`), поле бланка и XLSX. В Excel именованное поле называется `RepairCards_OneCCode`; при вставке строки/столбца в редакторе привязка перемещается вместе с ячейкой. Для печати CSV содержит `InternalID,ProductID,Platform,QRUrl,OneCCode`.

### Один раз настроить BarTender

1. В окне QR выберите **сетевой адрес** сервера, доступный остальным ПК/телефонам.
2. Нажмите «Сформировать QR». «Открыть в браузере» проверяет QR-ссылки, «Закрепленные файлы» открывает файлы отдельного задания.
3. Укажите `bartend.exe`, обычно `C:\Program Files (x86)\Seagull\BarTender Suite\bartend.exe`.
4. «Макет(BarTender)» открывает рабочий BTW. QR-объект должен иметь источник **«Поле базы данных → QRUrl»**. Приращение/сериализацию объекта отключите: значения уже сформированы программой.
5. Для кода 1С добавьте текстовый объект с источником **«Поле базы данных → OneCCode»**. Пустой код даст пустой объект. Подпись «Код 1С», положение, размер и шрифт задайте в самом макете.
6. Если поля не видны, подключите `labels.csv` текущего задания: первая строка — заголовки, разделитель — запятая, кавычки — двойные, кодировка UTF-8.
7. Сохраните рабочий макет Ctrl+S. Откройте «Предпросмотр / печать», выберите **Zebra S4M (203 dpi) – ZPL**, проверьте размер этикетки, качество/насыщенность, количество копий и записи. Кнопка «Образец» — штатный предпросмотр BarTender. Печать запускается вручную.
8. Первым прогоном напечатайте одну этикетку и сверьте сканирование и код 1С, затем печатайте диапазон.

Каждое задание имеет отдельные CSV/QR и отдельную копию BTW для печати, поэтому два Creator не подменяют друг другу источник одного открытого документа BarTender. Изменять макет нужно через «Макет(BarTender)», а не в копии задания. Внешние картинки/файлы макета должны иметь абсолютные пути. Одновременно сохранять один рабочий BTW из нескольких окон самого BarTender не следует.

Рабочая копия макета хранится в `%LOCALAPPDATA%\RepairCards\labels\RepairCards.btw`. У другого Windows-пользователя/на другом ПК свой макет и свой установленный принтер. Исходный TEST-original.btw встроен как болванка, не заменяет уже настроенный рабочий файл. Сам двоичный BTW программно не редактировался: привязки выполняются штатно в BarTender.

## 6. Reader и Repair — инструкция пользователю

1. Скопируйте **один** Reader.exe или Repair.exe из `clients` в любое удобное место и запустите. Можно запускать тот же файл несколько раз.
2. Сканируйте полную QR-ссылку в поле «QR / номер» и нажмите Enter либо «Открыть». Ссылка содержит адрес сервера и Unique ID.
3. Если вводите только внутренний числовой Unique ID, сначала укажите адрес сервера и подтвердите Enter. Внешний Table ID без типа не является однозначным адресом бланка.
4. После подтверждения адрес сохраняется, поле скрывается и становится неактивным. Нажмите надпись **«Сервер»**, чтобы открыть его снова.
5. Reader показывает отдельное встроенное окно просмотра. Repair открывает такое же окно для редактирования. Внешний браузер Windows-клиентам для бланка не нужен.
6. В Repair двойной щелчок по ячейке включает ввод. Сохранение — «Сохранить» или Ctrl+S. Можно добавлять строки/столбцы и менять оформление. Очередь и получение чужих сохраненных изменений работают автоматически.
7. Для следующего сканирования вернитесь в поле QR основного окна. Для нескольких одновременно открытых бланков запустите несколько экземпляров приложения.
8. При закрытии Repair с правками можно сохранить их или отменить закрытие. «Скачать мои правки (XLSX)» создает отдельную копию текущего варианта.

На телефоне QR открывает страницу просмотра обычным браузером в той же сети; живое обновление работает и там. Не выключайте серверный ПК во время работы пользователей.

## 7. История и восстановление бланка

Кнопка **«История»** показывает последние 200 сохраненных версий. В базе сохраняется вся история; ограничено количество строк в диалоге. История начинается с момента сохранения/назначения кода в новой версии, включая первоначальный вариант перед изменением. Более ранних, уже перезаписанных до обновления вариантов в старой базе нет.

- «Скачать XLSX» создает копию выбранной версии, не меняя текущий бланк.
- В Creator/Repair «Восстановить» после подтверждения ставит восстановление в ту же очередь. Текущий вариант остается в истории, выбранный становится **новой** сохраненной версией. Номер версии назад не откатывается.
- Остальные открытые окна получают восстановленный вариант через живое обновление. Их собственные несохраненные правки остаются местными и при последующем сохранении обрабатываются обычными правилами очереди.

История защищает от случайного более позднего изменения, но не заменяет резервную копию всего диска/базы. Она увеличивает размер SQLite; учитывайте свободное место на сервере.

## 8. Резервная копия базы

### Пока сервер работает

В `ready-windows` есть **`repair_backup.exe`**. Он использует SQLite Backup API, учитывает WAL и проверяет целостность результата. Пример из PowerShell в этой папке:

```powershell
.\repair_backup.exe --database "..\data\repair.sqlite3" --output "..\backups\repair-2026-11-14.sqlite3"
```

Укажите фактический путь вашей базы и новое имя копии. Существующий файл не перезаписывается. Ожидается `Backup completed; integrity_check: ok`. Итоговый файл появляется только после успешного копирования. Сервер и клиенты можно оставить работающими. Если интенсивная запись не дала закончить за 60 секунд, копия не публикуется — повторите позже или остановите сервер.

Не копируйте только `.sqlite3` Проводником при работающем сервере: часть новых данных может находиться в WAL. Для живого резервирования предназначен repair_backup.exe.

### Пока сервер остановлен

Сохраните бланки, остановите сервер и скопируйте всю `data` вместе с конфигом. Рабочий BarTender и клиентские настройки отдельно сохраняйте из `%LOCALAPPDATA%\RepairCards`. Копии лучше держать на другом диске/корпоративном хранилище.

### Восстановление всей базы

1. Закройте клиенты и остановите сервер.
2. Переместите текущую папку `data` целиком в отдельное резервное место. Не оставляйте старые `-wal`/`-shm` рядом с подставленной копией другой базы.
3. Создайте чистую `data`, поместите в нее резервный SQLite и укажите его имя в конфиге.
4. Запустите совместимую версию сервера, проверьте `/api/health`, количество карточек и несколько бланков. Откройте клиенты заново.

Восстановление базы возвращает состояние на момент копирования: более поздние изменения в этой копии отсутствуют.

## 9. Как обновлять потом

### Вариант А — новый однофайловый EXE

Самый простой способ для сотрудников:

1. Сохранить бланки и закрыть все экземпляры обновляемого приложения.
2. Получить новый Creator.exe/Reader.exe/Repair.exe и заменить прежний файл.
3. Запустить его. Новый комплект распакуется в свой каталог; настройки сервера и рабочий BTW сохранятся отдельно.

При откате замените EXE прежним. База при замене клиентского EXE не меняется. Старые каталоги кэша автоматически не удаляются: это позволяет сохранить откат. Старый EXE, уже пропатченный через DLL, будет использовать свой пропатченный каталог.

### Вариант Б — локальный ZIP-патч DLL

Этот вариант нужен, чтобы не заменять запускающий EXE при изменении клиентской логики.

1. Получите ZIP-патч **для вашей исходной версии**. Полный архив проекта не является DLL-патчем.
2. В меню окна через QR-иконку слева от заголовка выберите «Локальное обновление…». Откроется Updater. Сохраните бланки и закройте **все экземпляры этого комплекта на этом ПК**, оставив Updater открытым.
3. Выберите ZIP. Updater проверит исходную/целевую версии, ABI, архитектуру и SHA-256 файлов.
4. Нажмите «Установить» и дождитесь результата. Прежние файлы сохранятся в `.updates/backup-…` внутри каталога клиента.
5. Запустите прежний однофайловый EXE. Он использует уже обновленную DLL из своего кэша и не распаковывает исходную поверх патча. Версия видна в «О программе…».

Если клиент не открывается из-за прерванного обновления, запустите тот же однофайловый EXE с параметром **`--update`**, например:

```powershell
.\Repair.exe --update
```

Updater восстановит прерванную операцию. Его кнопка «Откатить обновление» возвращает предыдущие клиентские файлы. Параметр **`--files`** открывает каталог именно этого комплекта:

```powershell
.\Repair.exe --files
```

Нельзя обновить DLL, пока другие экземпляры **того же комплекта** используют ее: Updater попросит их закрыть. Другие ПК и другие комплекты со своей DLL продолжат работу. Ни один клиентский патч не заменяет SQLite, серверный конфиг, Excel-болванку или рабочий BTW.

### Серверные изменения

Обновление веб-редактора или серверной C++ логики выполняется на серверном ПК: резервная копия → остановка сервера → замена указанных файлов готового серверного комплекта → проверка конфига → запуск → проверка `/api/health` → повторное открытие бланков пользователями. Обновление сервера с изменением схемы всегда требует предварительной копии базы. Updater клиента сервер не обновляет.

Нельзя обещать, что произвольный новый C++ код заработает без сборки: новую DLL/серверный EXE собирает разработчик и выдает готовыми файлами. Пользователям компилятор не нужен. Для обычных изменений клиентской логики достаточно DLL, стабильный запускающий EXE остается прежним. Цвета/шрифт задаются theme.json, Excel-болванка и BarTender-макет редактируются своими средствами.

## 10. Где хранятся файлы

| Данные | Место |
|---|---|
| Карточки, текущие XLSX, коды 1С, история | SQLite на сервере, путь в конфиге |
| Общая Excel-болванка новых карточек | `templates/blank.xlsx` сервера |
| Веб-редактор для всех клиентов | `web` сервера |
| Настройки адреса клиента | `%LOCALAPPDATA%\RepairCards\creator.json`, reader.json, repair.json |
| Рабочий BarTender | `%LOCALAPPDATA%\RepairCards\labels\RepairCards.btw` |
| Файлы отдельных заданий | `%LOCALAPPDATA%\RepairCards\jobs` |
| Распакованные библиотеки/Updater/справка | `%LOCALAPPDATA%\RepairCards\clients\роль\идентификатор` |
| Профили встроенных окон | `%LOCALAPPDATA%\RepairCards\WebView2\роль\process-PID` |

Один EXE означает один **распространяемый** файл, а не отсутствие локального кэша. В кэше нет копии рабочей базы. Он общий для экземпляров одного комплекта у одного Windows-пользователя. На другом ПК/под другой учетной записью свои настройки и кэш.

При повреждении кэша сначала попробуйте `--update`. Если восстановить его нельзя: закройте все экземпляры, откройте `%LOCALAPPDATA%\RepairCards\clients\нужная роль`, переместите каталог соответствующего комплекта в резервное место и снова запустите EXE. Он создаст исходный комплект заново; установленные только в этом кэше DLL-патчи придется повторить. Не удаляйте всю RepairCards: там рабочий BTW и настройки. Профили WebView2 можно очищать после закрытия всех клиентов, если нужно освободить место.

## 11. Короткая проверка после установки

1. В одном Creator сформируйте пробный диапазон из десяти номеров. Во втором Creator дождитесь его появления без ручного обновления.
2. В двух Repair откройте одну карточку. В первом измените одну ячейку и сохраните; во втором другую и сохраните. Оба изменения должны остаться.
3. Измените в обоих одну ячейку и сохраните по очереди. Везде должно появиться последнее сохраненное значение. В «Истории» должны остаться оба варианта.
4. Откройте два Reader: они должны получить сохраненные правки автоматически, редактирование недоступно.
5. Назначьте коды `2 / 123`, `7 / 1234`, `1 / 12345`. Проверьте назначения в списке, бланках и CSV. Напечатайте одну пробную этикетку.
6. Создайте резервную копию через repair_backup.exe и убедитесь в сообщении `integrity_check: ok`.

Учетных записей и входов по вашим требованиям нет. Reader/Repair/Creator определяют интерфейс, а API сервера не разграничивает права по пользователям. Раздавать только Reader удобно для обычного просмотра; настоящие права доступа потребуют отдельного этапа, если они понадобятся.

## 12. Сборка разработчиком

Исходники рассчитаны на C++17, CMake 3.20+, Windows x64/MinGW64. В CLion откройте CMakeLists.txt. Для генерации однофайловых клиентов во время **сборки** нужен Python 3; для запуска готовых EXE он не нужен.

```text
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
```

Цели `repair_creator_portable`, `repair_reader_portable`, `repair_repair_portable` создают `build/portable/Creator.exe`, Reader.exe, Repair.exe. Обычная `repair_client` создает RepairClient.dll, `repair_server` — сервер, `repair_backup` — копирование базы.

Для будущего DLL-патча измените версию CMake, соберите Release-DLL и выполните:

```text
python scripts/make_patch.py --client-dir ПАПКА_СБОРКИ --from-version 0.6.0 --version 0.6.1 --output RepairCards-0.6.0-to-0.6.1.zip
```

По умолчанию включается RepairClient.dll. При необходимости добавьте `--file RepairClient.dll --file theme.json`. Сначала проверяйте патч на копии комплекта и совместимость с сервером. Пример показывает формат команды для будущей версии; не устанавливайте фиктивный патч без реальной новой DLL.

Результаты и границы автоматических проверок описаны в [VALIDATION.md](../VALIDATION.md). Проверка реального корпоративного маршрута, пользовательского BTW и физической Zebra выполняется на вашем ПК.

Для старого обычного комплекта 0.5.0 в релизе также есть реальный `RepairCards-0.5.0-to-0.6.0-client-patch.zip`. Его можно установить старым Updater **после обновления сервера/веб-файлов до 0.6**. Он обновляет общую DLL обычного комплекта; однофайловыми старые маленькие EXE от этого не становятся. Для раздачи одного файла используйте новые EXE из clients.
